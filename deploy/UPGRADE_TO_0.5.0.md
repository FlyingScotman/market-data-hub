# Обновление до 0.5.0 (контракт `market_snapshot/1.6`: календари SPFI, RUONIA, RUSFAR)

Для владельца. Записка готовится вместе с PR #81 (FlyingScotman/market-data-hub#38, бриф TDM
H17) и описывает релиз, который выпустит его после 0.4.0. Исходное состояние: production =
**0.4.0** (контракт `market_snapshot/1.5`, 45 миграций; [UPGRADE_TO_0.4.0.md](UPGRADE_TO_0.4.0.md),
FlyingScotman/market-data-hub#35). Порядок: сначала тег `v0.4.0` на `main` без PR #81, потом
слияние PR #81, потом этот релиз. Агент не ставил тег, не публиковал релиз и не трогал
production: всё ниже делает владелец. Задачу релиза 0.5.0 завести по образцу #35 и записывать
результаты в неё.

## Версия

Тег после слияния: **`v0.5.0`**, не 0.4.1. Правило репозитория (UPGRADE_TO_0.3.0,
UPGRADE_TO_0.4.0): новая минорная версия контракта — минорная версия хаба. Здесь контракт 1.6 и
миграция `0429_fixing_calendars`. `min_previous_version` не менялся (`0.1.0`): 0.5.0 ставится
прямо поверх 0.4.0 (и более ранних), промежуточных шагов нет.

## Что приходит

Контракт `market_snapshot/1.6` (аддитивно; полный список — `schemas/market_snapshot/v1/README.md`,
строка 1.6):

- **Календари** `MOEX_SPFI`, `CBR_RUONIA`, `MOEX_RUSFAR` в `calendars` static-среза (новые
  значения `calendar_code`) — календари, которые называют спецификации рублёвых свопов MOEX
  кроме MOSCOW (= `RU_PRODUCTION`):
  - `MOEX_SPFI` — торговые дни рынка СПФИ = рабочие дни `MOEX_FORTS`;
  - `CBR_RUONIA` — дни, за которые ЦБ рассчитывает и публикует RUONIA: рабочие дни
    `RU_PRODUCTION` без последнего рабочего дня каждого года и без нерабочих дней 2020 года
    по указам Президента;
  - `MOEX_RUSFAR` — дни расчёта рублёвого overnight RUSFAR: рабочие дни `RU_PRODUCTION` и
    `MOEX_STOCK` с понедельника по пятницу без последнего торгового дня года (с 2021), с
    курируемыми исключениями 2019 и 2022 годов.
- Календари выводятся из действующих дней базовых календарей по документированным правилам
  (источники `rule_moex_spfi`, `rule_cbr_ruonia`, `rule_moex_rusfar`) с курируемыми
  исключениями (источник `curated`, файл `mdhub/data/calendar_derived.json`, у каждой записи —
  первоисточник). День, флаг которого опирается на предварительный вход (непроверенный год
  `RU_PRODUCTION`, ещё не решённый конец года), пишется источником `rule_*_unverified` и
  учитывается в `provisional_from` календаря.
- Обновление календарей сверяет их с фиксингами: значение RUONIA или RUSFAR в день без расчёта —
  ошибка календаря (предупреждение, запуск `partial`, календарь не меняется).

**Потребители.** Каждый объект схемы — `additionalProperties: false`, а `calendar_code` —
перечисление. Потребитель, который строго проверяет 1.5, отклонит static-срез 1.6; читатель
«любой 1.x, неизвестное игнорировать» остаётся корректным (монитор ищет календари по имени).
Market-срезы меняют только `schema_version`.

## Миграции

Одна новая, аддитивная: `0429_fixing_calendars` — CHECK `ref.calendar_day.calendar` расширен
значениями `MOEX_SPFI`, `CBR_RUONIA`, `MOEX_RUSFAR`; функция `ref.calendar_source_rank` ставит
любой `*_unverified` (а не только `curated_unverified`) ниже правил; меняются комментарии.
Данные не переписываются, безопасно на заполненной базе (как 0422, 0428). Номер меньше уже
применённых — это нормально: `mdhub migrate` применяет все неприменённые файлы по имени и
проверяет контрольные суммы применённых.

После установки `/health/ready`: `applied` 46, `known` 46, `pending` 0, `checksum_mismatch` 0.
Новых настроек, секретов, заданий и источников нет.

## Выпуск и установка (штатный механизм Updates)

1. Слить PR #81 в `main` (после тега `v0.4.0`), дождаться зелёного CI на коммите слияния.
2. Поставить тег `v0.5.0` на коммит слияния (README_DEPLOY §11) командами git, не через браузер
   (причина — UPGRADE_TO_0.4.0, «Выпуск и установка», шаг 2):

   ```bash
   git switch main && git pull --ff-only
   git tag -a v0.5.0 -m "market-data-hub 0.5.0"
   git push origin v0.5.0
   ```

   - `git switch main` — перейти на ветку `main`; `&&` — следующую команду выполнить, только
     если предыдущая успешна; `git pull --ff-only` — подтянуть коммит слияния только перемоткой
     (без локального merge-коммита).
   - `git tag -a v0.5.0` — аннотированный тег; из него hatch-vcs берёт версию 0.5.0; `-m "…"` —
     сообщение тега.
   - `git push origin v0.5.0` — отправить тег в `origin`; это запускает `release.yml`
     (ci → build → sign с одобрением в окружении `release` → verify → publish).
3. Actions → workflow `release` → одобрить `sign`; дождаться GitHub Release с тремя файлами
   (`.tar.gz`, `.SHA256SUMS`, `.SHA256SUMS.minisig`).
4. Консоль хаба → **Updates** → 0.5.0 → «Review and install». На странице подтверждения — одна
   миграция `0429_fixing_calendars`. Updater проверит подпись, сделает дамп, остановит воркер,
   применит миграцию, перезапустит сервисы и проверит `/health/ready`; при ошибке откатится сам.

## После установки

1. **Разовое обновление календарей.** Плановый `cbr_meetings` пересчитывает календари только в
   первый рабочий день месяца (09:10 МСК); до него три новых календаря пусты и static-срез их не
   содержит. Чтобы записать их сразу — на сервере хаба, функцией `dc` (обёртка над
   `docker compose` с файлами установки, как в прошлых записках; её определение здесь не
   приводится):

   ```bash
   dc run --rm --no-deps worker mdhub run cbr_meetings -p mode=calendar
   ```

   - `dc` — `docker compose` с compose-файлами текущей установки;
   - `run` — выполнить команду в новом разовом контейнере сервиса; `--rm` — удалить контейнер
     после завершения; `--no-deps` — не запускать зависимые сервисы (база уже работает);
   - `worker` — сервис, в образе которого есть CLI `mdhub` и доступ к базе;
   - `mdhub run cbr_meetings` — выполнить задание `cbr_meetings` один раз (запись в
     `ops.job_run`, trigger `cli`);
   - `-p mode=calendar` — параметр задания (`-p` = `--param`, формат `ключ=значение`): режим
     ежемесячного запуска — обновить все календари (наблюдаемые, курируемые, правила, затем
     три выводимых с 2019 года и сверку с фиксингами), затем заседания ЦБ. Полный пересев
     (`mode=calendar_full`) не нужен.

   То же можно сделать с консоли: **Jobs** → `cbr_meetings` → «Run now» (параметры по
   умолчанию = `mode=calendar`). Результат — `/v1/runs?job=cbr_meetings`: ожидается
   `succeeded`. `partial` с сообщением `calendar CBR_RUONIA cross-check` или
   `calendar MOEX_RUSFAR cross-check` значит, что фиксинг вышел в день, который календарь
   считает нерасчётным: календарь не меняется, нужна курируемая запись в
   `calendar_derived.json` — завести issue с датой (без значений фиксинга).
2. **`snapshot_static`** — Jobs → «Run now» (иначе плановый в 07:45): static-срез 1.6 с
   одиннадцатью календарями.
3. Market-срезы 1.6 выйдут сами по расписанию.

## Проверка

Через read-API (токен в переменной окружения, не в команде):

```bash
H="Authorization: Bearer $MDHUB_TOKEN"; B="https://<hub host>"
curl -sS "$B/health/ready"
curl -sS -H "$H" "$B/v1/calendar?calendar=MOEX_SPFI,CBR_RUONIA,MOEX_RUSFAR&from=2026-12-28&to=2026-12-31"
curl -sS -H "$H" "$B/v1/calendar?calendar=CBR_RUONIA&date=2025-12-30"
curl -sS -H "$H" "$B/v1/snapshots?kind=static&latest=true"
```

- `H=…; B=…` — две переменные оболочки: заголовок авторизации (токен берётся из `$MDHUB_TOKEN`)
  и адрес хаба (`<hub host>` подставить); `;` разделяет команды.
- `curl` — HTTP-запрос; `-sS` — без индикатора прогресса, но с текстом ошибки; `-H "$H"` —
  добавить заголовок; аргумент в кавычках — URL (кавычки нужны из-за `?` и `&`).
- `/v1/calendar` — флаг рабочего дня по каждому (календарь, день) с источником наивысшего
  приоритета; `calendar=` — список календарей через запятую; `from=` / `to=` — диапазон дат
  включительно; `date=` — один день.

Ожидание:

## Откат

Updates → «Roll back» к 0.4.0 восстанавливает pre-update дамп (миграции есть): строки трёх новых
календарей и миграция 0429 уходят вместе с ним, остальные календари не затрагиваются. Ничего
невосстановимого 0.5.0 не копит — после повторной установки разовый `cbr_meetings` запишет
календари заново. Static-срезы 1.6, опубликованные до отката, неизменяемы; новые снова будут 1.5
с восемью календарями.
