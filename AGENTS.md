# AGENTS.md — market-data-hub

Инструкции для агентов (Claude Code и другие), работающих в этом репозитории. `CLAUDE.md` подключает этот файл.

## Правила проекта

- Каждую команду терминала, которую даёте владельцу, объяснять целиком: команду, подкоманду, каждый флаг, аргумент и
  оператор.
- Репозиторий **публичный**: без учётных данных и способа их построения, без адресов, путей и сведений о
  инфраструктуре продакшна, без данных организации.
- Изменения на продакшн-сервере делает владелец; у сессий доступ к хабу только на чтение.
- Issues хаба пишем по-английски, в сложившемся стиле: заголовок `Component: outcome`, в описании — проблема с
  доказательствами (коммит, file:line), критерии приёмки, координация.
- Разработка — `docs/DEVELOPING.md`; устройство — `docs/DESIGN.md`, `docs/SYSTEM_CONTEXT.md`.

- Для CodeGraph файл `codegraph.json` исключает `**/fixtures/**`: сохранённые тестовые данные не входят
  в локальный граф исходников. Штатный `exclude` действует при index, sync и watch; тесты вне fixtures остаются
  в индексе. При изменении исключений проверить состав индекса и сохранность исходников.

## CodeGraph: обязательный локальный индекс

Решение владельца от 27.10.2026: исходный код этого репозитория разрешено индексировать локально.
Раздел одинаковый во всех четырёх репозиториях программы; жизненный цикл обязателен для исполнителей и ревьюеров.

- Индекс принадлежит конкретному checkout/worktree. В новом checkout без `.codegraph/` выполнить в корне
  репозитория `codegraph init` до анализа кода. Не индексировать umbrella-каталог и не переиспользовать
  базу другого checkout. Если init предлагает Git hooks, выбрать ручной sync; не принимать установку hooks.
- При входе в checkout с существующим индексом выполнить `codegraph sync`. Повторять sync после
  checkout/pull/merge/rebase и после значимых изменений перед дальнейшим анализом. Перед передачей работы
  также выполнить `codegraph sync`, затем `codegraph status --json` и реальный запрос `codegraph explore`
  по существующему символу или пути вызовов; проверить непустой индекс и актуальность результата.
- Если `.codegraph/` существует, для понимания и поиска кода использовать CodeGraph прежде grep/find и чтения
  исходников: сначала MCP `codegraph_explore`, когда доступен (отложенный инструмент загрузить по имени),
  иначе CLI `codegraph explore "<символы или вопрос>"`. Запрос по имени файла или символа возвращает исходник
  с номерами строк и пути вызовов, включая переходы динамической диспетчеризации. Текстовый поиск допустим
  после CodeGraph для точных строк или непокрытого содержимого. Отсутствие MCP не блокирует CLI.
- Автообновление возможно при работающем MCP-сервере, но не предполагается и ручной sync не заменяет.
  Новый watcher, cron или framework для индексации не создавать. При ошибке индексации или устаревшем графе
  сообщить об этом и не выдавать результат за актуальный; устранить причину и повторить sync/status/explore.
- Хранить `.codegraph/` только локально, исключать из Git и поставляемых пакетов, архивов и образов.
  Индексировать только исходники данного репозитория: без реальных отчётов, секретов, приватных артефактов,
  архивов поставки, зависимостей и соседних checkout. Приватный исходный код разрешён только в локальном
  индексе; не переносить его или содержимое индекса в публичные issues, PR и отчёты.
- Ради индексации не менять глобальные настройки агентов и Git hooks. Перед запуском в другом checkout
  оркестраторы и суборкестраторы передают исполнителям и ревьюерам эти требования вместе с заданием;
  наличие наследуемых инструкций не предполагается.
- В облачных сессиях Claude Code CLI ставит SessionStart-хук `.claude/hooks/session-start.sh`: только при
  `CLAUDE_CODE_REMOTE=true`, без индексации; локально CLI ставит владелец. Хук одинаковый в четырёх репозиториях.

## Задачи ведём в GitHub Issues

Решение владельца от 23.10.2026. Правило общее для четырёх репозиториев программы:
[trading-desk-monitor](https://github.com/FlyingScotman/trading-desk-monitor) (монитор, TDM),
[market-data-hub](https://github.com/FlyingScotman/market-data-hub) (хаб),
[rub-fixed-income-core](https://github.com/FlyingScotman/rub-fixed-income-core) (ядро),
[trades-data-adapter](https://github.com/FlyingScotman/trades-data-adapter) (адаптер, приватный).
Текст раздела одинаковый во всех четырёх `AGENTS.md`. Если меняете его, поменяйте во всех четырёх.

**Единственный список работ — GitHub Issues.** Новых списков доработок в markdown, JSON, TODO-комментариях и
чатах не заводим. Старые трекеры (`backlog.json`, `OWNER_REQUESTS.md`, `STATUS.md` в мониторе, `docs/BACKLOG.md` в
ядре, `ROADMAP.md` хаба и адаптера) заморожены 23.10.2026: их открытые пункты перенесены в issues, новых пунктов туда
не добавляем. Сами документы остаются как история, описание стратегии и источник стабильных номеров (`B#45`, `R43`).

### Как устроено

```
Дорожная карта программы (корневой issue в trading-desk-monitor)
├── Эпик (метка epic): стратегическое направление, недели работы
│   ├── Задача: конкретная доработка, от часов до нескольких дней
│   └── Задача в другом репозитории (sub-issue может быть из любого из четырёх)
└── Мелкие доработки: <репозиторий> (постоянный эпик для потока небольших просьб)
```

- **Корень.** Один issue [«Дорожная карта программы»](https://github.com/FlyingScotman/trading-desk-monitor/issues/5)
  в trading-desk-monitor. Его sub-issues — все эпики всех
  четырёх репозиториев. Отсюда видно всю программу и прогресс каждого эпика.
- **Эпик** — issue с меткой `epic`. Живёт в репозитории, где лежит основная работа. Эпик, который в равной мере
  касается нескольких репозиториев, живёт в trading-desk-monitor. В описании эпика: цель, критерий готовности, что
  не входит. Задачи эпика — его sub-issues; GitHub сам показывает прогресс «N из M».
- **Задача** — обычный issue. У каждой задачи есть родитель: эпик или «Мелкие доработки: <репозиторий>». Задача
  заводится в том репозитории, где будет код.
- **Ошибки** помечаем стандартной меткой `bug`. Поле Type (Feature / Bug / Task) у репозиториев личного аккаунта
  GitHub не сохраняется, его не используем.
- **Метки** (одинаковые во всех репозиториях):
  - `epic` — эпик;
  - `bug` — ошибка;
  - `P0`…`P3` — приоритет: `P0` срочно (блокирует работу, риск утечки или потери данных), `P1` следующая очередь,
    `P2` нормально, `P3` когда-нибудь; ставим ровно одну;
  - `needs-owner` — ждёт владельца: решения, данных, доступа или действия на рабочей машине; в описании написано,
    что именно нужно;
  - `blocked` — ждёт другую задачу; ссылка на неё в описании;
  - `stream:…` — блок работ, ровно один на задачу: `stream:ui` (интерфейс), `stream:bugs` (баги),
    `stream:desk-data` (внутренние данные организации и новые продукты), `stream:calc` (расчётная логика и ядро),
    `stream:platform` (хаб, релизы, эксплуатация, процесс). Каждый блок ведёт своя сессия-оркестратор; список
    блоков и ссылки на выборки — в корневом issue. Задачу чужого блока сессия не делает: заводит issue с меткой
    того блока.
- **Ссылки между репозиториями** — полной формой `FlyingScotman/<repo>#N`. Голое `#N` GitHub считает номером в
  текущем репозитории. Номера из старых документов пишем с префиксом (`B#45`, `R43`, `WEB-7`, `DEC05`), чтобы
  GitHub не превратил их в ссылки на чужие issues.

### Что делает агент в каждой сессии

1. **В начале** найти открытые issues по теме сессии (поиск по репозиторию, эпики, `needs-owner`). Работать в
   рамках существующего issue, а не заводить параллельный.
2. **Просьба владельца в чате** (в том числе несколько мелких доработок одним сообщением) — сразу завести по issue
   на каждую, под нужный эпик или под «Мелкие доработки: <репозиторий>», и ответить владельцу списком ссылок.
   Мелочь, которую делаем тут же в этой же сессии, отдельного issue не требует: хватит PR.
3. **Нашли по ходу работы** ошибку, долг или идею вне текущей задачи — завести issue, а не TODO в коде или
   «осталось» в отчёте.
4. **PR** ссылается на issue: `Closes #N` или `Closes FlyingScotman/<repo>#N` закрывает его при слиянии; `Refs #N`,
   если PR закрывает задачу частично. Порядок ревью и слияния — ниже, «PR и ревью».
5. **В конце сессии** оставить в issue комментарий: что сделано, что осталось, на чём остановились. Следующая
   сессия начинает с него. Закрывать с причиной: `completed`, `not_planned` или `duplicate`.
6. Вопрос к владельцу — issue с меткой `needs-owner` (или комментарий в задаче, которую он блокирует), а не
   только строка в чате.
7. **Вопрос к владельцу пишем человеческим языком** — в чате, в issue, в PR. Он должен быть понятен человеку, который
   не читал переписку агента и не помнит номеров: что происходит, что именно нужно от владельца (решение, данные,
   доступ, действие на рабочей машине), какие есть варианты и что будет при каждом. Номер задачи (`#N`, `B#45`, `R43`),
   внутренний термин или сокращение описания не заменяют: ссылку можно дать рядом, но вопрос должен читаться и без
   перехода по ней. Плохо: «По #N — вариант B или C?». Хорошо: «Монитор показывает PnL по вчерашним ценам, если хаб
   не ответил. Оставить так или показывать пустую ячейку с пометкой „нет данных“? (FlyingScotman/trading-desk-monitor#N)».

### PR и ревью

- PR получает ту же метку `stream:…`, что и его issue, и строку `Closes FlyingScotman/<repo>#N`.
- У каждого блока есть сессия-ревьюер («Ревью: <блок>»). Оркестратор блока, открыв PR, сообщает о нём своему
  ревьюеру. Ревьюер проверяет PR. Если есть замечания, он оставляет их в PR и возвращает PR оркестратору. Если
  замечаний нет и CI зелёный, ревьюер сам сливает PR merge commit'ом. Владелец может слить или остановить любой PR
  сам.
- Без владельца ревьюер не сливает: релизы и теги, выкатку на продакшн, переписывание git-истории, удаление
  данных, изменения раздела о задачах в `AGENTS.md`. По таким PR он спрашивает владельца.
- Все сессии работают под одним аккаунтом GitHub, поэтому формальный approve невозможен. Итог ревью — комментарий
  в PR («ревью: можно сливать» или список замечаний).

### Что нельзя писать в issues

trading-desk-monitor, market-data-hub и rub-fixed-income-core — **публичные** репозитории, их issues видят все.
В них нельзя: цифры реальных позиций, книг и PnL; названия внутренних систем и отчётов организации, контрагентов,
оргструктуру; адреса и пути серверов, логины, ключи и способ их построения. Такое пишем в приватном
trades-data-adapter, а в публичном issue оставляем нейтральную формулировку и ссылку на приватный. В
trades-data-adapter тоже никогда не пишем значения ячеек отчётов, только названия полей и метаданные.

```
Связи: родитель, зависимости (FlyingScotman/<repo>#N).
```
